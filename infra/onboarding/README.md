# Cloudflare onboarding service

Implements [`spec.md` §15.11](../../spec.md) and Part A of the [onboarding spec](spec.md) (Cloudflare account → Bye hostname → first owner). The flow, UX and rules are defined there; this file covers running the service, where each requirement lives, and what is still open. Parts B and C run inside the deployed app ([Outside this service](#outside-this-service)).

It has not been run against Cloudflare. The acceptance scenarios (OB01–OB10 plus the standard-install tests) pass against fakes in `infra/tests/onboarding.test.ts`. The release gates below are still open.

There are two ways to run it. Both use the same service, HTTP handler (`http.ts`) and rules:

- **Hosted (default for new users):** a Cloudflare Worker at `https://bye.chr33s.dev` (`BYE_ONBOARDING_ORIGIN`, else `https://onboarding.<DOMAIN>`), with the Alchemy run executed by a deployer provisioned in the user's own account ([Hosted](#hosted)).
- **Self-hosted Node process:** `pnpm onboarding` on a machine with the release checkout, behind Cloudflare Access ([Run (Node)](#run-node)).

## Hosted

```text
onboarding.<DOMAIN> ─ Onboarding Worker ─ OnboardingDO (service + SQLite store + RemoteExecutor)
                                              │ user's OAuth token, Cloudflare API
user's account ─ images copied into registry.cloudflare.com/<account>/bye-*
               ─ <worker>-deployer Worker ─ Deployer DO ─ Container: pnpm run deploy (Alchemy)
```

| Piece                                   | File                                                           |
| --------------------------------------- | -------------------------------------------------------------- |
| Worker entry, `OnboardingDO`, heartbeat | `worker/onboarding.ts`                                         |
| Records on Durable Object storage       | `do-store.ts`                                                  |
| Bootstrap + plan/apply over HTTP        | `remote.ts`                                                    |
| Registry-to-registry image copy (OCI)   | `oci.ts`                                                       |
| Deployer Worker (uploaded to the user)  | `deployer/worker.ts`, bundled into `deployer/worker.bundle.ts` |
| Deployer container (Node, job API)      | `deployer/server.ts`, `deployer/Dockerfile`                    |
| Pinned release (tag, digests, metadata) | `release-pin.ts`, generated by `release-manifest.ts`           |
| Stack for the service itself            | `stack.ts` (`pnpm deploy:onboarding`)                          |

**Separate from the app.** The service is its own Alchemy stack (`ByeOnboarding`): `pnpm run deploy` never deploys it, only `pnpm deploy:onboarding` does. In CI it is opt-in: set the repository variable `BYE_ONBOARDING` to `true` and the `onboarding` job in `ci.yml` deploys it from `main`, and `release-images.yml` builds the release images on version tags. Both skip otherwise.

**Deploy the service** (Bye's account; the page is `BYE_ONBOARDING_ORIGIN`, else `https://onboarding.<DOMAIN>`; its host must be in a zone on the account):

```sh
BYE_ONBOARDING_ORIGIN=https://bye.chr33s.dev \
BYE_ONBOARDING_KEYS=v1:$(openssl rand -hex 32) \
BYE_ONBOARDING_SESSION_KEY=$(openssl rand -hex 32) \
BYE_ONBOARDING_DEPLOYER_KEY=$(openssl rand -hex 32) \
CLOUDFLARE_OAUTH_CLIENT_ID=… \
pnpm deploy:onboarding
```

- **CI:** the `onboarding` environment holds `BYE_ONBOARDING_KEYS`, `BYE_ONBOARDING_SESSION_KEY`, `BYE_ONBOARDING_DEPLOYER_KEY`, `CLOUDFLARE_OAUTH_CLIENT_SECRET` (optional) and the prod `PROD_CLOUDFLARE_*` / `PROD_BYE_STATE_*` credentials, plus the variables `BYE_ONBOARDING_ORIGIN` (`https://bye.chr33s.dev`), `CLOUDFLARE_OAUTH_CLIENT_ID` and optionally `BYE_ONBOARDING_ACCESS_TEAM_DOMAIN` / `BYE_ONBOARDING_ACCESS_AUD`; `DOMAIN` is the repository variable the release jobs use. `pnpm plan:onboarding` previews a change.
- **Keys:** escrow all three. `BYE_ONBOARDING_KEYS` seals credentials and runtime secrets (losing it loses the generated secrets). `BYE_ONBOARDING_SESSION_KEY` signs session cookies (rotating it signs everyone out). `BYE_ONBOARDING_DEPLOYER_KEY` derives each installation's deployer secret (rotating it makes existing deployers refuse until the next bootstrap re-uploads them).
- **Identity:** session mode by default: the operator is the signed session, so anyone can start and only that session can act. Set `BYE_ONBOARDING_ACCESS_TEAM_DOMAIN` and `BYE_ONBOARDING_ACCESS_AUD` to require Cloudflare Access instead.
- **Release:** `release-pin.ts` is the pinned release; until it names one, the page reports "no release pinned" and nothing can be installed. Publish a release with `node --experimental-strip-types infra/onboarding/release-manifest.ts <tag> <image digests…>` (see the file header) after CI has pushed the four `linux/amd64` images to GHCR as public packages.
- **Deployer lifecycle:** bootstrap runs before every plan and is idempotent (spec Part J §44). The deployer stays in the user's account after install; it holds no credentials and only answers requests signed with its secret.
- **Durable Object restarts:** a deployment survives them (spec Part J §47). The apply runs as a job on the deployer, the operation records the job, and the heartbeat alarm wakes an evicted DO, which follows the job again (or re-runs the read-only reconcile and health steps). Only an operation that can't continue safely is marked `interrupted`.
- **Lost session:** a new session that connects Cloudflare is offered **Resume your Bye** for the account's existing installation (spec Part J §43); the old session loses access.

## Run (Node)

```sh
BYE_ONBOARDING_ORIGIN=https://onboard.example.com \
BYE_ONBOARDING_DATA_DIR=/var/lib/bye-onboarding \
BYE_ONBOARDING_KEYS=v1:$(openssl rand -hex 32) \
BYE_ONBOARDING_OPERATOR_HEADER=cf-access-authenticated-user-email \
BYE_ONBOARDING_ACCESS_TEAM_DOMAIN=https://<team>.cloudflareaccess.com \
BYE_ONBOARDING_ACCESS_AUD=<Access application AUD tag> \
CLOUDFLARE_OAUTH_CLIENT_ID=… \
BYE_RELEASE_DIR=/srv/bye-release BYE_RELEASE_VERSION=v1.0.0 \
pnpm onboarding
```

- **`BYE_RELEASE_DIR`** is a clean checkout of the published tag `BYE_RELEASE_VERSION`, with dependencies installed (`pnpm install --frozen-lockfile`). The release identity is the tagged commit plus the lockfile digest. If the checkout moves, every later deploy fails revalidation until the operator approves the new release.
- **`BYE_ONBOARDING_KEYS`** encrypts stored OAuth credentials and generated runtime secrets. It uses the same `v2:<hex>,v1:<hex>` rotation shape as the state backend, and the installation ID is the AAD. Escrow it: losing it loses the generated secrets (`SESSION_KEY` etc.) needed for later upgrades.
- **Operator identity** comes from Cloudflare Access: the service verifies the `Cf-Access-Jwt-Assertion` JWT on every request (RS256 signature against the team's `/cdn-cgi/access/certs` keys, cached; `iss` = the team domain; `aud` = `BYE_ONBOARDING_ACCESS_AUD`; `exp`/`nbf`) and uses its `email`. The identity header named by `BYE_ONBOARDING_OPERATOR_HEADER`, if present, must agree; on its own it is never trusted (`access.ts`). `BYE_ONBOARDING_LOCAL_OPERATOR=<name>` runs a single-operator local instance instead. With no identity proxy in front, local mode makes the peer prove it is the operator: it refuses to start on a non-loopback `HOST`, and at startup prints a per-process bearer token and a one-time login URL (`<origin>/login?code=…`). Opening the URL once sets an authenticated session cookie (always a fresh session; a pre-existing cookie is never promoted), and API clients send `Authorization: Bearer <token>`. Every `/api/*` route and the OAuth callback refuse other peers with 401, even when they forge `Origin`; only the static page and its assets are served without it. Both values die with the process; restart to get a new login link.
- **Host check:** every request's `Host` must equal the host of `BYE_ONBOARDING_ORIGIN` (else 421), so a DNS-rebinding page can't read even the GET routes. A proxy or tunnel in front must forward the public host unchanged; in local mode set the origin to the URL you open (for example `http://localhost:8788`).
- **Network:** the server listens on `127.0.0.1` by default; publish it through a Cloudflare Tunnel protected by the Access application. Set `HOST` (for example `0.0.0.0`) only in Access mode when another trusted proxy must reach it, and never expose the origin without Access in front.
- **Sessions:** the `__Host-` session cookie is HMAC-signed by the server (per-process key), so a client can't choose or plant a session id (session fixation); an unsigned or forged cookie is replaced. The OAuth callback must come from the same session **and** the operator who owns the installation. The service needs HTTPS (or `localhost`).
- **Pending OAuth state** (PKCE verifiers) expires after 10 minutes and is swept at startup, every 10 minutes and on each new authorization.
- **CSP:** the page's script and styles are served same-origin (`/app.js`, `/app.css`); the policy has no `'unsafe-inline'`.
- **Startup:** operations left `queued`/`running` by a previous process are marked `interrupted` and their writer locks released.

### Stack changes

`BYE_WORKERS_DEV_NAME`, which only onboarding sets, fixes the Worker names so the origins are known before the first deploy:

- MailCore is `<name>`, PublicSite `<name>-site`, and the new `RenderOrigin` forwarder `<name>-render`.
- MailCore also gets the chosen hostname as its custom domain (`APP_DOMAIN`, `APP_ORIGIN=https://<hostname>`). The public site and `RenderOrigin` stay on workers.dev, so there is no second domain decision.
- workers.dev stays enabled on persistent stages. Version preview URLs stay off.
- Outbound personal mail is on: onboarding generates an RSA-2048 DKIM key (`MAIL_DKIM_PRIVATE_KEY`, sealed and in the recovery kit), sets `MAIL_DKIM_PUBLIC_KEY` (published at `bye1._domainkey.<domain>` by incoming-email activation) and `MAIL_TRAFFIC_CLASSES=transactional,personal`. Personal mail goes through Cloudflare Email Sending (the `send_email` binding); there is no external personal-mail provider.
- Newsletter dispatch qualification comes only from the pinned release: `infra/release/qualification.json` (`{"newsletter": "<evidence ref>"}`) becomes `NEWSLETTER_QUALIFIED`. Absent, newsletters stay unavailable.
- No `SignupChallenge` Turnstile widget: the first account uses `BOOTSTRAP_TOKEN`.
- Push notifications are on by default (a checkbox at "Create Bye", and a setting under "Recovery and connection" that redeploys through a review). Onboarding generates a VAPID key (`VAPID_PRIVATE_KEY`, sealed) and derives `VAPID_PUBLIC_KEY`. Turned off, both are deployed empty and the sealed key is kept. Installations bound before push existed get a key on their next review. The recovery kit always carries the VAPID private key (generating it first if needed), plus `push.enabled` and the public key to set when push is off, so a redeploy from the kit keeps existing devices. Native apps receive push through Bye's push gateway (`workers/push-gateway`), not through anything in the user's account.
- Non-secret installation metadata reaches MailCore: `BOOTSTRAP_ADDRESS_DOMAIN` (the zone) plus `INSTALL_ACCOUNT_ID`, `INSTALL_ZONE_ID` and `INSTALL_ZONE_NAME`, which incoming-email activation binds to. The generated `NEWSLETTER_CONFIG_SEAL_KEY` seals the newsletter provider credentials entered on first use. `ZONE_TOKEN_SEAL_KEY` seals the optional Cloudflare token (limited to the installation zone) the owner can enter so incoming-email activation runs through the zone API instead of manual records (`infra/RUNBOOK.md`).
- `RenderOrigin` gives the separate render origin (§10) a second hostname without a custom domain. Its only binding is MailCore, which serves just `/render/*` and `/img` on that host.

Unset (every CI-managed stage), the stack is unchanged. `guard-stage.ts` accepts `BYE_DEPLOY_WRITER=onboarding` in place of `CI=true` for shared stages. Production still needs `BYE_RELEASE_MANIFEST_VERIFIED=1`, which the service sets only after the approval digest matches a fresh plan.

### First account and recovery (§8–§9)

- **First account:** onboarding generates `BOOTSTRAP_TOKEN` with the other secrets and, once ready, navigates to the §9 URL. The claim is a single D1 row (`0032_instance_bootstrap.sql`, `workers/core/src/bootstrap.ts`); a signup that fails after claiming releases the slot, and a claim abandoned mid-signup can be retaken after five minutes. The web app's `#bootstrap=` handling is tested in `apps/web/test/bootstrap.test.ts`. With the token unset (every CI-managed stage), signup is unchanged.
- **Recovery kit:** downloaded once via `POST /api/recovery-kit` from "Recovery and connection". Beyond the §8 fields it holds the stage, state reference, URLs, release and the full stack configuration with the generated secrets, so the installation can be redeployed without this service. The service records when it was issued, never its contents, and refuses a second download.

## Provisional decisions

The open decisions in spec.md §14 item 16 are resolved provisionally as follows. Each needs sign-off before release.

- **State backend:** `Cloudflare.state()` in the operator's account, so the operator owns state too. The strict profile's HTTP backend is not offered.
- **Executor location:** hosted, a deployer Worker + Container in the operator's own account, one job at a time (spec Part J). Self-hosted Node, the onboarding host, one child process per operation.
- **Stages:** `POST /api/bind` (account + stage: `prod`, `staging`, or a `dev-<id>` trial) stays for internal, test and operator use; `preview-*` belongs to CI.
- **Existing installation:** a first deploy whose plan contains anything but creates is blocked. Onboarding does not adopt another deployment.
- **Hostname conflicts:** before binding, a public DNS-over-HTTPS lookup refuses a Bye address that already has records, because a Worker custom domain never overrides one. A zone wildcard can't be told apart and is allowed. Until the first deployment write (and before the recovery kit is issued), a standard install may move to another hostname; afterwards the target is fixed. Planned hostnames are recorded in the plan export (`domains`), and anything other than the chosen hostname on MailCore blocks the review.
- **Reconnect and re-review:** with an expired or disconnected authorization the page keeps the installation and offers **Reconnect Cloudflare**. Failures whose next action is a fresh review (release or plan changed, reconcile mismatch, interrupted) offer **Review the plan**. The one-time setup link is served only through `POST /api/first-account`.
- **Upgrades:** no separate upgrade flow. Pinning a newer release makes the next review show its actions and migrations, and the same approval, serialization and recovery rules apply. Nothing upgrades automatically.
- **Health:** the checks above. They say nothing about inbound mail.

## Open before release

- **OAuth client:** Bye's Cloudflare OAuth client registration, redirect URI, and whether a client secret is issued. The endpoints default to the dashboard ones Wrangler uses.
- **Scope verification:** scope IDs follow Cloudflare's OAuth catalog as mirrored in Alchemy (`alchemy/src/Cloudflare/Auth/OAuthScopes.ts`), and every plan type is covered, including R2 (`workers-r2.write`), the state store's Secrets Store, and `zone.read` + `workers-routes.write` for the custom hostname. Every entry is still `verified: false`, so every `prod` install lands in `needs-review` with coverage blockers (never auto-approved) until a nonproduction deploy with exactly this set succeeds. Documentation does not prove OAuth compatibility. Record the run below and flip the flags.
- **Custom domain:** a real custom-domain deploy, and recovery from an interrupted one, must succeed before release. Certificate issuance can delay the first health checks; retrying with the same approval reruns them. In alchemy `2.0.0-beta.79` the custom domain is part of the MailCore Worker row; a release that emits a separate `Cloudflare.Workers.CustomDomain` row is permitted only for MailCore.
- **Token lifetime:** Alchemy's Cloudflare client sends an OAuth access token and an API token identically (`Authorization: Bearer`), so `CLOUDFLARE_API_TOKEN` works as the carrier. Alchemy treats that env token as non-expiring and cannot refresh it. The service therefore refreshes right before each run, and a single plan or deploy must finish within one access-token lifetime (about an hour). Measure a full first deploy, containers included, during the nonproduction run.
- **Account prerequisites:** the Workers plan needed for Containers, Durable Objects and Queues is shown to the operator but not checked by the API.
- **Hosted mode:** the open items in spec Part J §46: registry-credential and container-application coverage of the scope set, a plan job still running across a restart, and deployer teardown on disconnect.
- **Short addresses on the first account:** addresses of four characters or fewer are a paid product, and signup refuses them without a completed checkout, which a self-hosted instance can't provide. The first account needs a longer address.
