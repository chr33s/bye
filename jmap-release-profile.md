# JMAP release profile

**Profile version:** 1. **Spec:** `spec.md` §16 (v2), Contract D2.
**Status: signed off 2026-10-12 by chris (chr33s@icloud.com). The 20 defects from the post-sign-off review are fixed, and the deployed suite was re-run on the fixed build (9/9).** Local and Cloudflare dev-stage evidence covers every field, along with the platform-constraint recheck and provider approval at the published `send_email` caps. Production activation proceeds per account through `POST /v1/ops/jmap/migrate` canaries (step 3 below), within the measured envelope.

## How to use this profile

1. Fill each field with the measured value and a link to the evidence (run logs, dashboards, test output).
2. Run the D1 test groups (below) on the release build and attach their output.
3. Activate canaries only through `POST /v1/ops/jmap/migrate` (`start`, then a separate `activate`). Activation is the no-backend-rollback point (C3).
4. Bump the profile version for every change to a supported limit.

| Durable Object   | Requests | CPU                                    | Duration  | Rows read / written | CPU or memory limit errors |

| MailboxDO        | 1,756    | 5.45 s (3.1 ms per request on average) | 20.4 GB-s | 1,654,264 / 20,598  | 0 / 0                      |
| IngressJournalDO | 502      | 0.25 s                                 | 1.5 GB-s  | 1,505 / 0           | 0 / 0                      |
| SearchShardDO    | —        | 8 ms                                   | 0.02 GB-s | 9 / 23              | 0 / 0                      |

Cost model, at Workers Paid list prices of 2026-10-12 (developers.cloudflare.com/durable-objects/platform/pricing and /workers/platform/pricing):

- **Ingest:** about 41 SQLite rows written per ingested Email (≈ $0.04 per 1,000 Emails at $1.00 per million rows written, beyond the included 50M a month).
- **Requests:** $0.15 per million Durable Object requests and $0.30 per million Worker requests.
- **Open streams dominate the cost.** An EventSource stream holds a streaming response from the account's MailboxDO, so the object can't hibernate while any stream is open. Duration is billed at 128 MB per active object. An account with a client connected all month costs 0.125 GB × 2,592,000 s = 324,000 GB-s, about $4.05 at $12.50 per million GB-s. That is per account, not per stream: concurrent streams share the one active object. Fleet sizing must assume always-connected clients cost this, or move the fan-in onto hibernatable WebSockets. Polling or `/changes` clients cost only their requests.

Defects found and fixed by these runs:

- The restore route polled the restarted object through the stub it had reset. A stub is unusable after its object resets, so every deployed restore timed out before replay, with the dispatch hold left on. `routes/ops.ts` now polls through fresh stubs.
- The platform-limit recheck found statements that could exceed Cloudflare's 100 bound parameters (see the platform constraints below).

### Re-run on the fixed build (2026-10-12)

The deployed suite was re-run on the fixed build against a fresh `dev-jmapev1` stage: 500 messages, 50 concurrent clients, 9/9 checks. The stage was then destroyed. The new check confirms that a default agent credential (`read`+`draft`) is refused submission, flagging and Empty Trash (`forbidden`), and that it may destroy drafts only.

The first re-run found one more defect, in usage rather than in any check. MailboxDO rows written per Email rose from ~41 to ~94 and duration from 20.4 to 45.3 GB-s. Now that every arrival emits a `shared.delivery` event, each one arms an immediate alarm. The alarm's `retryArrivals` then re-prepared arrivals that were still in flight: a second R2 read and parse, and an extra attempt counted, so overlapping alarms could even park a healthy arrival. The alarm now retries only arrivals whose backoff has passed (`JmapIngest.due`), with a regression test. After redeploying:

The recheck matches the planning baseline. `CORE_LIMITS` stays inside it: 50 recipients per submission matches the provider cap. One gap surfaced and was fixed. Three statements could exceed 100 bound parameters:

- the email and thread reads, when a delegated viewer had more than 10 readable mailboxes alongside a 90-id chunk;
- `inMailboxOtherThan`, which binds a list supplied by the client;
- session restore generations, for a principal with 100 or more accounts.

Each list is now bound as a single JSON parameter through `json_each(?)`, with a regression test in `packages/platform-cloudflare/test/jmap-core.test.ts`.
