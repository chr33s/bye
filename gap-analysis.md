## 2. Cross-cutting themes

1. **Store logic without HTTP routes or UI.** The main gap. Domain, organization, sharing, World, billing, calendar-read and many mailbox operations are written and unit-tested in the stores, but nothing reaches them over HTTP, and the clients have no controls for them. Examples:
   - Mail and sending: sender-policy history, recent searches, Focus & Reply, Read Together, merge history, labels/rules lists, attachment library, file links, send-job outcomes.
   - Org and account: team admin (roles, remove, reactivate, members, seats, audit), invitation acceptance, org creation, recovery codes, TOTP enrollment, passkey management.
   - Sharing and publishing: share-grant revoke, public-link preview and revoke, spaces/comments/collections.
   - Calendar: calendar reads (week tasks, habits, timer, journal, day context, calendar list), feed tokens.
   - Exports: no download route.
2. **Async topics that are acked and dropped.** In `workers/core/src/consumers.ts`, these queue messages are consumed but nothing happens: `blob-gc`, `notify`, `calendar.notify`, `calendar.subscription.refresh`, and `forwarding-verification` (which goes through notify). As a result:
   - Blobs are never collected.
   - There are no notifications or reminders.
   - ICS subscriptions fetch zero times.
   - Forwarding destinations can never be verified.
3. **Transport and abuse controls.**
   - Only the Transactional and Personal adapters are wired. The Forwarding, Subscription and External-identity adapters are not.
   - There is no SRS/ARC.
   - There are no sending budgets, ramp-up, suppression lists, compromise detection or outbound suspension.
   - World fanout marks recipients "sent" without sending anything.
4. **Correctness and security defects.** A small set of real bugs; see §3.
5. **Release pipeline.** The plan-policy check never sees a real `alchemy plan`. Production approval happens before the plan is generated. There are no post-deploy probes, canary, two-deploy test, or restore drills.
6. **Client parity.** The web and native apps are thin: read-mostly views, a plain composer, and no calendar editing. Mobile sign-in doesn't use the device-session model.
7. **§14 evidence still open.** Provider approvals, SMTP retry behaviour, wire Message-ID, performance, and a real deploy/rollback with Workflows in flight.

## 5. Suggested sequencing

1. **P0 defects (§3).** Mostly small, contained fixes with regression tests. The Screener bypass, remote-images preference, search Trash leak, redelivery crash and forwarding verification should come first.
2. **Handle every async topic.** Blob GC, notify/push, calendar notify, subscription refresh and forwarding verification. Then per-topic replay from source state (dispatch in `ready`, index, propagate) and wider catalog reconciliation.
3. **Routes and UI for existing store logic.** Security settings (recovery codes, TOTP, passkeys, sessions, tokens), team and domain admin, export downloads, sharing and public links, calendar reads and editor, and the mailbox operations listed in §4.1.
4. **Transport and abuse.** Forwarding (SRS/ARC), subscription and external-identity adapters, budgets, suppression, entitlement enforcement.
5. **Release pipeline.** Real plan→policy gate, plan-then-approve-then-deploy, post-deploy and canary probes, two-deploy test, restore drills, preview sandbox.
6. **Evidence (§14).** Stage 0 deployment against approved providers, SMTP and Message-ID fixtures, performance, and a rollback drill with in-flight work.
